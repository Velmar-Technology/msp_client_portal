Rol: Actúa como un Desarrollador Full-Stack Senior y Arquitecto de Software.  Objetivo: Desarrollar un Sistema de Mesa de Ayuda (Help Desk) utilizando una Arquitectura Monolítica basada en Capas y el Stack PERN (PostgreSQL, Express, React, Node.js).  Requerimientos Funcionales:Módulo del Cliente:Creación de Tickets: El sistema debe permitir la generación de tickets capturando toda la información detallada del problema. Debe incluir soporte estructurado para la subida de archivos adjuntos.  Trazabilidad: Los clientes deben poder seguir el flujo de sus tickets, conociendo tanto el movimiento físico de sus equipos como el estado del problema de su servicio.  Comunicación Omnicanal: Debe existir una facilidad de comunicación 1 a 1 con el servicio al cliente, integrando vías como Gmail, WhatsApp y teléfono.  Regla de Negocio (SLA): El sistema debe contemplar restricciones de tiempo, permitiendo ciertas acciones (como cancelaciones o modificaciones) solo durante 1 hora después de haber generado el ticket, específicamente para casos de servicios o garantías.  Módulo del Equipo / Operaciones:Recepción y Categorización: El sistema debe gestionar la recepción de todos los tickets y peticiones, subdividiéndolos automáticamente en categorías: reparación, garantía de artículos o servicios caídos.  Asignación Inteligente: Se debe implementar una distribución de los tickets de forma rotativa (Round-Robin) entre los técnicos disponibles. Además, el sistema debe contemplar la optimización y asignación a especialistas específicos (por ejemplo, técnicos especializados en TV).  Notificaciones Automáticas: El sistema debe contar con automatización para el envío de mensajes de estado al cliente (por ejemplo: "su dispositivo está en proceso", "su dispositivo está en espera del pago para iniciar").  Requerimientos Técnicos y Arquitectura de Calidad (Best Practices):Stack Tecnológico Core:Frontend: React (SPA) manejando el enrutamiento y el estado de la UI.  Backend: Node.js con Express, estructurado estrictamente en capas (Rutas, Controladores, Servicios, Repositorios).  Base de Datos: PostgreSQL.  Código Base: El código debe ser limpio, modular y estar fuertemente tipado (se requiere el uso de TypeScript).  Diseño de Arquitectura Backend:Arquitectura Inspirada en Onion / Clean Architecture: Mantener el monolito, pero aplicar límites estrictos de dependencia: la lógica de dominio no debe depender de la base de datos ni del framework web.Patrones de Diseño: Implementar el Patrón Repositorio (Repository Pattern) para aislar las consultas a la base de datos. Utilizar Servicios Genéricos para manejar el mantenimiento de datos (CRUD) y aplicar lógicamente los principios de CQRS separando las operaciones de lectura (queries) de las de escritura (commands) a nivel de servicio.Seguridad y Autenticación:JWT y RBAC: Implementar seguridad robusta mediante JSON Web Tokens (JWT) y Control de Acceso Basado en Roles (Role-Based Permissions) para aislar las vistas y acciones entre Clientes, Técnicos y Administradores.Manejo de Contraseñas: Asegurar los flujos de "Confirmación de Correo" y "Recuperación de Contraseña".Resiliencia, Monitoreo y Validaciones:Pipeline de Validación: Implementar middlewares de validación robustos (ej. usando Zod o express-validator) para asegurar que ninguna petición malformada llegue a los controladores. Utilizar DTOs y mapeadores para la transferencia de datos.Manejo Global de Excepciones: Crear un middleware centralizado para capturar, formatear y estandarizar todas las respuestas de error de la API.Logging Profesional: Integrar una librería de registro estructurado (ej. Winston o Pino) para auditoría y trazabilidad de errores en el servidor.Pruebas y Despliegue:Testing: Diseñar los servicios y repositorios de manera que sean inyectables (Dependency Injection principles) para facilitar las Pruebas Unitarias.CI/CD: Preparar el proyecto para flujos de trabajo automatizados usando GitHub Workflows para validación de código y despliegue automatizado. Integrar documentación automatizada de la API (Swagger/OpenAPI).
